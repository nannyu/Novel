# PRD 撰写规范

> 本文件供 product-planner skill 在撰写 PRD 时按需参考。

---

## 1. PRD 的核心原则

### 1.1 写给谁看

PRD 有多类读者，写法要满足所有人的核心需求：

| 读者 | 关心什么 | 写法要点 |
| --- | --- | --- |
| 开发工程师 | 边界条件、数据格式、异常处理、接口细节 | 具体、可操作，避免模糊描述 |
| 测试工程师 | 验收标准、测试路径、异常场景 | 明确的通过/不通过条件 |
| 业务负责人 | 功能是否符合业务目标、范围是否合理 | 业务语言，联系业务价值 |
| 设计师 | 页面布局、交互流程、视觉规范 | 页面描述清晰，有流转关系 |

### 1.2 好 PRD 的标准

- **完整**：所有功能点都有描述，没有「后续补充」的空洞占位
- **明确**：每个功能的触发条件、处理逻辑、输出结果都清晰，没有歧义
- **可测试**：验收标准用「可以/不可以」「成功/失败」等可判断的语言写
- **有边界**：明确说明「不在范围内」的内容，防止范围蔓延
- **可追溯**：每个需求有来源（来自调研报告、客户访谈、业务目标等）

## 2. 各章节写作要点

### 第 1 章：产品概述

**产品定位（一句话）**的好坏对比：

- 差：「本系统是一个综合性的信息管理平台。」
- 好：「面向社区网格员的移动端工作台，将日常巡查、事件上报、任务跟进三类工作统一在一个 App 中，减少多系统切换。」

**目标用户**要写具体角色，不要写「用户」：

- 差：「所有使用本系统的用户」
- 好：填写角色表，含角色名称、岗位、主要诉求、使用频率

### 第 2 章：功能需求

每个功能点的标准写法：

```markdown
#### 功能点：批量导入居民信息（编号：2.1.3）

**业务背景**：网格员需要在系统初始化时一次性导入辖区内居民信息，
手动录入效率极低，需要支持 Excel 批量导入。

**主流程**：
1. 用户点击「批量导入」按钮
2. 系统弹出文件选择框，限定格式为 .xlsx / .xls
3. 用户选择文件后，系统解析文件，展示预览（前 5 行数据 + 总行数）
4. 用户确认后，系统开始导入，显示进度条
5. 导入完成后，展示「成功 N 条，失败 M 条」汇总，可下载失败记录

**异常处理**：
- 文件格式不符：提示「请上传 .xlsx 或 .xls 格式文件」
- 文件超过 10MB：提示「文件过大，请拆分为 10MB 以内的文件分批导入」
- 字段缺失/格式错误：在失败记录中标注原因，不影响其他行的导入

**业务规则**：
- 单次导入上限：5000 条
- 必填字段：姓名、身份证号、住址（缺少任一则该行导入失败）
- 重复数据：以身份证号去重，重复行跳过，计入「失败」
- 导入日志：记录操作人、时间、文件名、成功/失败数量，保留 90 天

**验收标准**：
- [ ] 上传合法格式文件，成功触发预览
- [ ] 上传非 xlsx/xls 文件，出现正确错误提示
- [ ] 导入 1000 条数据，3 分钟内完成
- [ ] 失败记录可下载，含原因说明
```

### 第 3 章：页面设计

不要只写「参见原型」，要补充原型中体现不出的逻辑：

- 字段为空时的默认值/占位文字
- 列表默认排序规则
- 搜索匹配规则（精确/模糊，哪些字段参与搜索）
- 权限控制（哪些角色能看到/操作这个页面）

### 第 5 章：数据需求

写数据字典时要包含：

| 字段名 | 类型 | 长度/格式 | 必填 | 唯一 | 默认值 | 说明 |
| --- | --- | --- | --- | --- | --- | --- |

特别注意写清楚：
- 时间字段的时区（默认 UTC+8）
- 金额字段的精度（保留几位小数）
- 枚举字段的所有可选值

## 3. 常见写法错误

### 3.1 模糊描述

| 错误写法 | 修正写法 |
| --- | --- |
| 「系统应快速响应」 | 「API 响应时间 P99 ≤ 500ms，页面首屏加载 ≤ 3s」 |
| 「支持多种格式」 | 「支持 .xlsx、.xls、.csv 三种格式」 |
| 「用户友好的界面」 | 「操作成功/失败均有 Toast 提示，3 秒后自动消失」 |
| 「需要权限控制」 | 「仅系统管理员和部门负责人可访问，其他角色跳转至无权限提示页」 |

### 3.2 遗漏异常场景

每个功能必须考虑：
- 输入非法时怎么处理？
- 网络超时/接口报错时怎么处理？
- 并发操作（多人同时编辑同一条数据）怎么处理？
- 数据量超出预期时（如列表 10 万条）怎么处理？

### 3.3 验收标准写得无法测试

- 差：「功能运行正常」
- 好：「用户在空列表状态下点击「新建」，弹出表单；填写所有必填字段后点击保存，新记录出现在列表第一行」

## 4. 不同类型产品的写法重点

### To G / 政府类产品

- 强调合规性：数据留存期、审计日志、等保要求
- 角色与权限描述要细：按单位、岗位、功能点的三维权限矩阵
- 导出功能重要：Word/Excel/PDF 导出，格式要符合政府文件规范

### To B / 企业管理系统

- 业务流程描述要完整：审批链、状态流转图、通知规则
- 数据一致性要求高：跨模块数据引用的同步规则
- 批量操作是高频需求：导入/导出、批量修改/删除

### 移动端产品

- 网络不稳定场景：离线缓存、断网提示
- 操作简化：单次操作步骤不超过 3 步
- 输入法适配：表单字段明确输入类型（数字键盘/文字/选择）

## 5. PRD 版本管理规范

- 每次版本更新必须填写变更记录表（在「文档信息」章节）
- 版本号规则：`v1`, `v2`, `v3`（整版变更）；小改动可注释但不升版本号
- 旧版本 MD 文件保留，不覆盖（按日期+版本号命名）
- 关联功能清单的版本号在 PRD 「基本信息」表中注明
