# LLM Wiki 知识库

## 目的

使用此技能处理遵循持久 `sources_dir -> wiki -> output` 模式的知识库。wiki 是核心阅读层和第二大脑工作层，不只是源材料索引；日常查询、输出文章、方案、项目规划时优先基于 `wiki/`，只在需要核查细节、追溯来源或重新分析时回到 `sources_dir/`。

- `sources_dir/`：源材料，只读，名称可配置
- `wiki/`：由代理维护的已编译Markdown wiki
- `output/`：派生输出，如Q&A答案、编译报告、健康检查
- `AGENTS.md` 或 `AGENTS.md`：该知识库的模式/操作契约

不要假设源材料目录名为 `raw/`。它可能是 `youdao/`、`sources/`、`clippings/` 或任何其他用户定义的路径。

## 根目录解析

将当前Cursor工作空间根目录视为知识库根目录，除非用户明确指定其他位置。

然后按以下顺序解析路径：

1. 如果存在，读取根目录的 `AGENTS.md` 或 `AGENTS.md`。
2. 使用模式文件确定：
   - 源材料目录
   - wiki目录
   - 索引文件
   - 维护日志文件
   - 任何页面结构规则
3. 如果没有模式文件：
   - 对于 `create knowledge base` 任务，先询问或推断预期的源材料目录并创建模式。
   - 对于 `compile/query/health-check` 任务，先停止并要求用户创建或批准模式文件。

## 触发短语（摘录）

下列表述应触发本技能；**完整中英列表**见 [references/reference.md](references/reference.md) 中的「触发词表」一节。

- 初始化或编译 wiki、导入源材料、问知识库、健康检查
- 归集知识点、先总结源材料/只写 output、总结后再入库
- 人物档案、人物画像、项目档案、项目画像、对象型页面、我的判断、关系状态、当前结论、时间线
- 书本镜像、方法论镜像、把某本书和我的经历/做法对应、把书里的流程编译成我的方法论
- 原始资料抽取、预处理资料、整理会议/图片/语音/截图、按我的方法论输出
- 自我模型、我的表达风格、使用反馈回写、第二大脑健康检查
- wiki 查重、是否已有相同总结、`/llm-wiki-kb` 显式调用

## 标准目录

模式应定义或暗示这些路径：

- `<sources_dir>/`
- `wiki/`
- `output/`

个人第二大脑型知识库可在 `wiki/` 根部维护核心页：`自我模型.md`（当前身份、长期方向、原则、偏好和当前判断）与 `我的表达风格.md`（文章、方案、汇报、PPT 的表达偏好和禁忌）。

推荐的派生输出路径：

- `output/qa/<YYYY-MM-DD>/<slug>.md`
- `output/wiki-compile/<YYYY-MM-DD>-compile.md`
- `output/wiki-health/<YYYY-MM-DD>-health-check.md`
- `output/extract/<YYYY-MM-DD>/<slug>.md`（**源材料抽取 / 预处理**：从混乱、多模态或会议类资料中抽取时间、地点、人物、事件、结果、用户判断和关联对象）
- `output/summary/<YYYY-MM-DD>/<slug>.md`（**源材料总结**的中间稿/定稿留痕，便于审计与二次编辑）
- `output/wiki-dedupe/<YYYY-MM-DD>-<slug>.md`（**查重/比对记录**：可选，但在「已存在同质总结」分支建议写入，避免只在聊天里口述路径）
- `output/book-mirror/<YYYY-MM-DD>/<slug>.md`（**书本镜像 / 方法论镜像**：把书本原理与用户自己的事迹、想法、做法建立对应关系，作为后续 wiki 编译依据）

## 多模态进入知识库的规则

多模态资料先进入 `output/extract/...` 做结构化抽取，不能因为资料形式新鲜就直接堆进 wiki。wiki 只接收经过说明、归因、时间化和对象关联后的二阶材料：语音需文字摘要；图片/截图需说明、时间、场景和关联项目；视频需关键片段和结论；外部资料需写「为什么收藏」和「对我有什么用」。缺少元信息时列为「待补信息」，不要直接编译进 wiki 结论。模板见 `references/reference.md` 的「多模态进入知识库规则」。

## Wiki 知识点文件命名（主题优先）

**文件名表达主题，不表达「从哪份源提炼」**：`知识点-*.md` 是可演进、可合并多源的**主题主页**；材料出处只写在页内 **`实体`（材料来源 / 对应源材料）** 的可点击链接列表中，避免一排平行页如 `从A提炼的X`、`从B提炼的X`。

- **默认禁止**自动生成：`知识点-从<源文件名>提炼的<主题>.md`、`知识点-<源>笔记之<主题>.md` 等**来源导向**文件名（除非用户**显式**要求该字面文件名）。  
- **用户未指定目标路径时**：先查重是否已有同主题的 `知识点-<主题>.md`；**有则增量合并**（补 `实体` 来源、修订五段），**无则提议** `知识点-<简短主题>.md`（主题取自用户任务或材料标题，在编译报告中说明映射）。  
- **多源同一主题**：只保留**一个**主题文件名；新源上线 → 更新该页 **实体** 来源列表与相关段落，并在 `_维护日志.md` 记「合并而非新建」。  
- **与仓库契约的关系**：若根目录 `AGENTS.md` / `AGENTS.md` 已规定命名（如「主题优先」），**以仓库为准**；本节约定为跨项目默认，仓库可收紧或覆盖。

### 简洁与可识别（默认）

目标：**文件名里的主题片段一眼可知讲什么**，且尽量短，避免把「整句标题」或「空话」焊进 `知识点-*.md`。

- **中文主题名长度**：默认倾向 **4～12 个汉字**（概念性名词短语）；专名、不可拆分的术语可略超出，但须在编译报告中注明理由。英文主题名倾向 **2～6 个词**（名词性短语为主）。
- **结构**：优先 **「核心对象 / 概念」**，或 **「对象 + 最短限定」**（如「X 与 Y」「X 配置」「X 工作流」）；避免口号式整句、问句、逗号长句。
- **建议省略的赘词**（除非它们本身就是讨论对象）：如「关于」「浅谈」「整理」「笔记」「记录」「学习」「总结」「一文读懂」「如何」「怎样」等——**压缩为名词性主题**；材料出处仍只放在 **`实体`** 链接，不靠拉长文件名表达来源。
- **消歧**：仅当 wiki 内已有同名或易混主题时，加 **最短限定词**（工具名、子域、版本其一即可），而不是把源文件名整段并入主题名。
- **用户显式给出文件名**：以用户字面为准，**不得擅自改名落盘**；若明显冗长或含赘词，可在回复与编译报告中**给出更短备选**供用户下次采用。
- **从源标题映射到页名**：当源 Markdown 标题**明显长于**上述长度或为口号句时，将主题**压缩为**符合本节的名词短语后再写入 `知识点-<主题>.md`；凡**本次新建页**且存在「源小节标题 / 原标题 → 采用页名」的映射，**必须**在 `output/wiki-compile/<YYYY-MM-DD>-compile.md` 中逐条列出对照（见下「编译输出」），便于检索与审计。

## 普通知识点页面结构

`知识点-*.md` 默认使用五段结构：`摘要` → `实体` → `概念` → `对比` → `概述与综合`。普通知识点不强制写「当前结论」「观点演化」「已废弃观点」「可复用规则」；这些内容只在用户明确要求、库内已有对应段落，或作为人物、项目、方法论等对象页规则时使用。

## 知识点编译维度（用户自定义与默认）

**编译维度**：把源材料映射到 wiki 时的**切分与组织方式**（例如按章节、按概念、按时间线、一页一主题、按用户自定义大纲等）。

- **用户显式指定时**：以用户当次给出的编译维度为准（优先级最高），据此拆分主题、命名或映射到目标 `wiki/.../知识点-*.md`（及模式规定的段落）；与用户指定冲突时不得擅自改用其它维度。
- **用户未指定编译维度**、仅泛泛要求「把这篇/这份笔记编译进 wiki」「按这份材料归集知识点」等时：**默认优先按源文件的 Markdown 标题结构**划分知识点边界——以 `#` / `##` / `###` 等标题作为自然主题单元；标题文本经 **「Wiki 知识点文件命名」→「简洁与可识别」** 压缩后写入 `知识点-<主题>.md`（具体是「多标题合并为一页」还是「一标题一页」由模式文件、目标路径与用户是否给出单页目标共同决定；在编译报告中说明映射关系，**新建页**须含「原标题 → 采用页名」对照）。
- **源材料没有可用标题**（如连续正文、纯列表、无层级标题的速记）：由代理**自拟提纲**归纳主题并完成编译，**不得**因缺标题而停滞；在对应页的 `实体` 和/或 `output/wiki-compile/...` 中**简要说明**所采用的归纳依据（便于审计与复核）。

上述默认不改变「查重先于落盘」「wiki 为二阶摘要非全文镜像」等其它强制规则。

## 原始资料抽取与预处理

当源材料是会议、会谈、语音、语音转写、图片、截图、视频、视频摘录、聊天记录、零散日记、外部资料或混乱长文时，先按上文「多模态进入知识库的规则」做结构化抽取，再决定是否总结或编译。抽取的目标不是得出最终结论，而是把资料整理成后续 wiki 可用的事实骨架。

抽取字段优先包括：时间 / 时间范围、地点 / 场景、人物 / 组织 / 项目 / 物件、发生了什么、结果 / 后续动作、用户自己的判断或原话（只整理，不替用户发明）、关联源材料与附件路径、待确认问题。

输出路径：`output/extract/<YYYY-MM-DD>/<slug>.md`。抽取稿可作为 `output/summary/`、`output/book-mirror/` 和 wiki 编译的输入。若抽取内容涉及人物、项目、书本镜像或方法论，应执行实体传播，更新对应对象页或方法论页的入口。

## 对象型页面编译（人物 / 项目）

当编译对象是人物或项目时，不使用普通 `知识点-*.md` 五段结构，也不使用 `知识点-<对象名>.md` 命名。人物页命名为 `人物-<人物名称>.md`；项目页放在对应项目文件夹内，命名为 `项目-<项目名称>.md`，作为该项目文件夹的总体说明页，项目文件夹内其它专题内容仍用 `知识点-<主题>.md`。

人物页固定结构为：**基本信息 → 互动时间线 → 当前状态 → 我的判断 → 关系状态 → 注意事项 → 相关项目 → 相关原始资料**；「基本信息」只写事实，「我的判断」只写用户本人明确表达的判断并标注更新时间。项目页必须有顶部「当前结论」：是否值得继续、当前阶段、最大问题、下一步、我现在的态度。若旧判断被新判断取代，在相关页追加「已废弃观点」表：`时间 / 旧观点 / 为什么废弃 / 替代观点`。详细模板见 `references/reference.md` 的「对象型页面模板」。

## 用户定向归集、源材料总结与查重（与任务 3/4/5 配合，强制顺序）

**执行顺序（一句话）**：锁定范围 → 查重（A/B/C）→ 分支落盘（dedupe 记录 / summary / wiki）→ 索引与日志。

本节处理两类常见指令：（1）**按用户指定**把内容归集进 wiki；（2）**先总结** `<sources_dir>` 中某段材料，结果默认进 `output/`，且在**写入总结文件或改写 wiki 之前**必须先做 wiki 查重。A/B/C 分支的字段说明与表格化对照见 [references/reference.md](references/reference.md) 中的「查重判定与分支」一节。

### 1）范围锁定（每次执行前先做）

从用户当次消息与仓库 `AGENTS.md` / `AGENTS.md` 中解析并**复述确认**（若用户未给全，再最小追问一次）：

- **源范围**：一个或多个 `<sources_dir>/...` 路径（文件或目录）。
- **编译维度**（若用户未说则按上一节**默认**：有标题按标题、无标题自拟提纲）：用户自定义维度优先。
- **目标**：要新建或更新的 `wiki/.../知识点-*.md`（或其它模式文件规定的页面名）；是否限定某些段落。**若用户未给文件名**：遵守上文 **「Wiki 知识点文件命名（主题优先）」**，不得默认使用「从某某提炼」式命名。
- **产物**：仅 `output/summary/...`、仅 wiki、或「summary → wiki」链式交付。

**优先级**：用户明确给出的路径、**编译维度**、**目标页路径/命名约束** **高于** 代理自拟主题切分；不得擅自扩大源范围或改目标页名，除非用户授权「你来拆分/命名」——即使用户授权代命名，仍须遵守 **主题优先**（除非用户明确要求来源式文件名）。

### 2）Wiki 查重（在「执行总结」或「大规模编译」落盘之前必须做）

目的：避免对**同一源范围、同一稳定结论**重复造页或重复写 summary。

**推荐操作顺序**（从快到慢，可组合）：

1. 读 `wiki/INDEX.md` 与相关子域 `INDEX.md`，列出与主题可能相关的 `知识点-*.md`。
2. 在工作空间内检索：用户给出的**源路径字符串**是否已出现在某些 wiki 页的 `实体` / 「对应源材料」/ 正文 Markdown 链接中。
3. 打开**少量高命中**页面，比对：
   - **源覆盖**：该页是否已声明覆盖本次用户指定的源路径集合（相同、子集、超集、或仅交叉）。
   - **结论同质**：`摘要` 或「概述与综合」中的**稳定论断**是否与本次将要输出的总结语义等价（不仅是关键词撞车）。

**判定标签**（写入查重记录或对用户说明时选用）：

- **A 完全同质**：同源同结论，已有 wiki 页可视为「相同总结」。
- **B 部分重叠**：源有交集但结论或边界不同 → 适合**增量修订**指定页，而非新建同质页。
- **C 无相关覆盖**：未发现已有页覆盖本次源范围 → 可按用户指令继续总结与/或编译。

### 3）分支行为（与用户要求对齐）

- **若判定为 A（完全同质）**：
  - 在回复中**明确提示** wiki 已存在相同或等价的总结，并给出 **Markdown 相对路径链接**（可点击跳转），可列多页。
  - 建议写入 `output/wiki-dedupe/<YYYY-MM-DD>-<slug>.md`：记录命中页、比对依据、源路径集合。
  - **默认不**再新建同质 `知识点-*.md`，也**默认不**再写入一份「内容相同」的 `output/summary`（除非用户明确要求留档对比稿）。
  - 若用户随后要求「仍要覆盖 / 合并修订 / 只更新某一段」，再在其指定下执行。

- **若判定为 B**：优先在**既有页面**上合并；更新索引与维护日志；编译报告注明「合并而非新建」。

- **若判定为 C（无同质）**：
  1. 若用户要**先总结**：将总结写入 `output/summary/<YYYY-MM-DD>/<slug>.md`（须含源链接与日期；模板见 `references/reference.md`）。
  2. 若用户要求「无同质则**编译为 wiki**」或总结完成后明确要入库：按模式文件结构写入/更新 wiki，走下方「### 4. 摄入和编译Wiki」的检查清单，并写 `output/wiki-compile/...`。

### 4）「把某知识点归集为一个 wiki」的快速路径

视为任务类型 3 的特例：**不做无根据的全库扫描**，严格按用户给定的源范围与目标页执行；若查重发现目标主题已被其它页覆盖，改为**更新**该页并在编译报告中说明原因。

## 书本镜像与方法论编译

当用户指定一本书、文章、课程或某套理论，并要求与自己的事迹、想法、做法建立对应关系时，执行「书本镜像」。它是半自动流程：用户指定书籍 / 方法论并最终确认；LLM 负责找对应经历、解释相似点、推导可复用方法。不要让 LLM 自己乱选书、乱套模型。

执行顺序：

1. **范围锁定**：确认用户指定的书本/理论来源、用户自己的记录来源、是否指定要编译进某个 wiki 页面或子域。若用户没有指定书籍/理论，先追问，不自行选择。若用户已明确给出路径，严格使用该范围。
2. **先读索引和相关 wiki**：查看是否已有该书、该理论、相关人物/项目/方法论页，避免重复建页。
3. **提取书本方法论**：从书本中提取原则、流程、判断框架、关键概念和适用边界；不要把书本全文镜像进 wiki。
4. **映射用户经验**：把书中每个可用方法论对应到用户给出的事迹、想法、做法或项目经历。没有真实对应时明确写「暂无对应」，不要强行牵连。
5. **写入 output**：先生成 `output/book-mirror/<YYYY-MM-DD>/<slug>.md`，保留书本依据、用户经验依据、对应关系、空白与待补材料。
6. **用户确认后编译进 wiki**：若映射形成稳定方法论，先标注需要用户确认的判断；经用户确认或已有明确判断依据后，更新或创建相应 `wiki/.../知识点-*.md`。若映射主要服务人物/项目对象页，则更新对象页的「我的判断」「当前状态」「当前结论」或时间线。所有 wiki 变更都要更新索引和维护日志。

注意：「我的判断」只能来自用户本人明确表达。LLM 可以整理用户判断，但不能替用户决定一本书、一个人、一个项目或一种做法对用户意味着什么。

## 任务类型

有七种标准任务类型。

### 1. 创建知识库

当用户想要初始化新知识库时使用。

检查清单：

```text
知识库初始化
- [ ] 确认知识库根目录
- [ ] 确认源材料目录名称/路径
- [ ] 创建 AGENTS.md 或 AGENTS.md
- [ ] 创建 wiki 索引结构
- [ ] 创建维护日志文件
- [ ] 创建输出目录或记录其约定
```

工作流：

1. 确认知识库根目录。
2. 确认源材料目录路径。
3. 创建 `AGENTS.md` 或 `AGENTS.md`，声明：
   - 源材料目录
   - wiki目录
   - 输出目录
   - 索引/日志约定
   - wiki页面结构
4. 初始化wiki骨架：
   - `wiki/INDEX.md`
   - 任何子域 `INDEX.md`
   - 维护日志文件，如 `_维护日志.md` 或 `log.md`
5. 保持源材料目录不变，除非在那里放置源文件。

### 2. 原始资料抽取与预处理

当用户要求整理会议、会谈、语音、图片、截图、视频、聊天记录、零散日记或混乱长文，并希望后续进入 wiki 时使用。该任务可单独执行，也可作为摄入编译、书本镜像或对象页更新的前置步骤。

检查清单：

```text
原始资料抽取
- [ ] 锁定源材料路径和附件路径
- [ ] 识别资料类型（文字 / 语音转写 / 图片 / 截图 / 视频摘录 / 会议 / 聊天）
- [ ] 按资料类型补齐入库前置规则：语音需文字摘要；图片需说明、时间、场景、关联项目；视频需关键片段和结论；外部资料需写为什么收藏和对我有什么用
- [ ] 抽取时间、地点、人物、项目、事件、结果、用户判断、待确认问题
- [ ] 记录所有源材料链接
- [ ] 写入 output/extract
- [ ] 判断是否需要继续总结、书本镜像或编译进 wiki
- [ ] 涉及人物/项目/方法论时执行实体传播
```

工作流：

1. 读取根目录 `AGENTS.md`，确认本库源材料和 wiki 规则。
2. 按用户指定路径读取源材料；不扩大范围，除非用户授权。
3. 按资料类型补齐必要元信息后，将结构化抽取写入 `output/extract/<YYYY-MM-DD>/<slug>.md`；缺少元信息时列入「待补信息」，不要直接编译进 wiki。
4. 如果用户要求继续入库，基于抽取稿进入「摄入和编译Wiki」或「书本镜像与方法论编译」。
5. 如果抽取内容涉及人物、项目或方法论页，更新对应页面入口、当前状态、我的判断或时间线，并记录维护日志。

### 3. 对象型页面编译（人物 / 项目）

当用户要求建立、更新、整理人物档案、人物画像、项目档案、项目画像，或源材料明显围绕某个人/项目持续积累时使用。

检查清单：

```text
对象型页面编译
- [ ] 判断对象类型：人物 / 项目
- [ ] 读取 wiki 索引，检查是否已有对象页
- [ ] 新建时按对象类型命名：人物-<人物名称>.md / <项目文件夹>/项目-<项目名称>.md
- [ ] 人物页按固定结构更新：基本信息、互动时间线、当前状态、我的判断、关系状态、注意事项、相关项目、相关原始资料
- [ ] 项目页顶部必须更新「当前结论」：是否值得继续、当前阶段、最大问题、下一步、我现在的态度
- [ ] 锁定源材料和用户明确表达的“我的判断”
- [ ] 我的判断只整理用户判断，必须标注更新时间，不替用户下结论
- [ ] 若新判断取代旧判断，追加「已废弃观点」表，不让旧观点与新观点平级
- [ ] 时间线只追加或标注修订原因，不无痕覆盖
- [ ] 更新索引和维护日志
```

工作流：

1. 从 `wiki/INDEX.md` 和相关子域 `INDEX.md` 查找现有对象页。
2. 若已有对象页，增量更新；若没有且对象会持续出现，按对象命名规则新建：人物用 `人物-<人物名称>.md`；项目在对应项目文件夹内创建 `项目-<项目名称>.md`，作为该文件夹总体说明页。项目文件夹不存在时，先创建项目文件夹、`INDEX.md` 和 `_维护日志.md`。对象页不得命名为 `知识点-<对象名称>.md`。
3. 人物页只把稳定事实写入「基本信息」，将新增事件按时间写入「互动时间线」，将现在在做什么写入「当前状态」。
4. 仅把用户本人明确表达的判断写入「我的判断」，必须标注更新时间；如果缺少用户判断，写「待用户判断」或提出少量问题。
5. 人物页维护「关系状态」「注意事项」「相关项目」「相关原始资料」；关系状态只能从约定集合中选择或标注待确认。
6. 项目页先更新「当前结论」，让最新判断位于页面顶部；然后再追加时间线、相关资料和专题互链。
7. 若新资料推翻旧判断，把旧判断移入「已废弃观点」表，记录废弃原因和替代观点。
8. 对相关人物、项目、方法论页做互链，并更新索引与 `_维护日志.md`。

### 4. 摄入和编译Wiki

当用户添加新源材料并希望将其编译到wiki中时使用。

核心规则：wiki是已编译的二阶叙事，不是源文件的全文镜像。

**编译维度**：遵循上文「知识点编译维度（用户自定义与默认）」——用户指定维度优先；未指定时默认按源文件**标题**切分，无标题则自拟提纲并在报告/实体中说明。

若用户**同时**要求「先总结再决定」或「总结进 output」，须先完成上文 **「Wiki 查重」** 再落盘；若用户仅说「按我指定的知识点归集」，仍建议在写入前对**目标主题**做一次快速查重以免重复建页。

检查清单：

```text
摄入和编译
- [ ] 先读取wiki索引
- [ ] （若用户要总结或指定源范围）先执行查重并分支
- [ ] 读取相关源材料
- [ ] 确定受影响的知识页面
- [ ] 更新或创建wiki页面（新建页主题名遵守「简洁与可识别」，默认中文 **4～12 字**）
- [ ] 普通知识点按五段结构维护：摘要、实体、概念、对比、概述与综合
- [ ] 为每个引用添加显式链接（源材料+其他知识点）
- [ ] 更新链接和索引
- [ ] 追加维护日志
- [ ] 将编译报告写入output（**新建页**若压缩原标题，须含「原标题 → 采用页名」对照）
```

工作流：

1. 先读取 `wiki/INDEX.md` 和相关的子域 `INDEX.md` 文件。
2. 从 `<sources_dir>/` 读取新源材料。
3. 确定影响集：
   - 新知识页面
   - 更新现有页面
   - 纠正过时的陈述
   - 添加反向链接
   - 合并或拆分主题
4. 使用模式定义的结构更新每个目标 `知识点-*.md` 或等效页面。
5. 如果使用普通 `知识点-*.md` 结构，保持五段顺序：摘要、实体、概念、对比、概述与综合；不要为了凑结构硬加当前结论、观点演化、已废弃观点或可复用规则。
6. 在 `实体` 中，明确记录对象、路径和相应的源材料；**多源**时用列表逐条可点击链接（**材料来源**），使该页成为可审计的汇集入口。新建**汇集型**主题页时，可在 `摘要` 首句标明「汇集型 / 多源可增量修订」。
7. 链接规则（强制）：
   - 任何引用的源材料必须是可点击的Markdown链接到其路径，例如 `[记录.md](../../youdao/随写漫谈/记录.md)`。
   - 任何引用的知识点必须是可点击的Markdown链接到其页面，例如 `[知识点-AI工具与内容生产.md](知识点-AI工具与内容生产.md)`。
   - 避免没有链接的纯文本引用；wiki必须是可导航的。
8. 更新wiki页面之间的相对链接。
9. 使用以下内容更新子域 `INDEX.md`：
   - 知识点列表
   - 源材料列表
10. 如果子域列表发生变化，更新根目录 `wiki/INDEX.md`。
11. 追加维护日志。
12. 将编译报告写入 `output/wiki-compile/<YYYY-MM-DD>-compile.md`。

### 5. 查询知识库

当用户提出应从wiki中回答的问题时使用。

检查清单：

```text
知识库查询
- [ ] 先搜索wiki索引
- [ ] 读取相关wiki页面
- [ ] 若任务需要体现用户判断方式或表达风格，优先读取 `wiki/自我模型.md`、`wiki/我的表达风格.md`，再读相关知识点、人物/项目/方法论页
- [ ] 仅在需要时读取源材料
- [ ] 使用路径引用编写答案
- [ ] 将答案保存到output/qa
- [ ] 决定是否适合wiki归档
```

工作流：

1. 从 `wiki/INDEX.md` 开始。
2. 读取最相关的wiki页面。
3. 当用户要输出文章、PPT、项目规划、方案、汇报或任何需要体现“我的判断方式/表达风格”的内容时，按顺序读取：`wiki/自我模型.md`、`wiki/我的表达风格.md`、相关 `知识点-*.md`、相关人物/项目/方法论页面；用其中的流程、判断标准和表达禁忌组织输出，而不是只复述事实资料。
4. 仅当wiki不足时，从 `<sources_dir>/` 读取需要的源材料。
5. 使用清晰的路径引用合成答案。
6. 始终将Q&A结果保存到 `output/qa/<YYYY-MM-DD>/<slug>.md`。
7. 如果答案只是一次性响应，仅保存在 `output/qa/...` 中。
8. 如果答案是稳定的知识点或对现有知识页面的有力补充：
   - 推荐归档到wiki
   - 仅当用户要求或模式明确允许自动归档时，才归档到 `wiki/`
9. 如果归档到wiki，还要更新索引和维护日志。

### 6. 健康检查和维护

当用户要求检查或维护知识库时使用。

检查清单：

```text
Wiki健康检查
- [ ] 查找矛盾
- [ ] 查找过时的声明
- [ ] 查找孤立页面
- [ ] 查找缺失的概念页面
- [ ] 查找缺失的反向链接
- [ ] 识别需要新来源的数据空白
- [ ] 检查第二大脑项：重要知识点缺少稳定摘要或概述、旧判断未在相关对象页或方法论页标明取代关系、高频主题缺综合判断、输出反馈未回写、`自我模型.md` / `我的表达风格.md` 过时
- [ ] 将报告保存到output/wiki-health
```

工作流：

1. 读取根目录和子域索引。
2. 采样相关的wiki页面和日志。
3. 检查：
   - 页面间矛盾、过时声明、孤立页面、缺失概念、缺失互链、来源空白
   - 第二大脑检查项：知识点摘要与概述质量、旧判断取代关系、综合判断、反馈回写、自我模型和表达风格时效性
4. 将报告保存到 `output/wiki-health/<YYYY-MM-DD>-health-check.md`。
5. 如果用户批准修复，更新wiki、索引和日志。

### 7. 书本镜像与方法论编译

当用户要求把「某本书 / 理论 / 文章 / 课程」和「我的经历 / 想法 / 做法 / 项目记录」做对应，并希望写入 output 或编译进 wiki 时使用。

检查清单：

```text
书本镜像
- [ ] 锁定用户指定的书本/理论来源；未指定时先追问，不自行选择
- [ ] 锁定用户自己的记录来源
- [ ] 读取 wiki 索引，检查是否已有相关书本、方法论、人物或项目页
- [ ] 提取书本方法论，而非全文复述
- [ ] 建立「书本原则 ↔ 用户事迹/做法」对应关系
- [ ] 无对应处明确写空白，不强行牵连
- [ ] 保存镜像报告到 output/book-mirror
- [ ] 将需要用户确认的判断标注清楚；经用户确认或已有明确判断依据后，再将稳定结论编译进 wiki，并更新索引/日志
```

工作流：

1. 读取根目录 `AGENTS.md`，确定本库是否已有对象型页面、人物/项目/书本页等特殊结构。
2. 按用户指定路径读取书本材料和用户自己的记录材料；如果用户只说“找本书套一下”，先追问具体书或方法论。
3. 生成 `output/book-mirror/<YYYY-MM-DD>/<slug>.md`，作为可审计中间产物。
4. 判断哪些内容适合进入 wiki：用户确认后的稳定方法论进入知识点页；涉及人物/项目的更新进入对应对象页；仅一次性联想保留在 output。
5. 更新 wiki 后同步更新 `INDEX.md` 与 `_维护日志.md`，并在 `output/wiki-compile/...` 中记录本次编译。

## 输出规则

### Q&A输出

每个知识库问题必须在 `output/qa/...` 下创建可重用 Markdown；**章节结构模板**见 [references/reference.md](references/reference.md) 中的「Q&A输出模板」一节。

### 原始资料抽取输出

- **抽取稿**：当源材料混乱、多模态、会议类或用户要求先整理事实骨架时，写入 `output/extract/<YYYY-MM-DD>/<slug>.md`（字段与模板见 `references/reference.md`）。
- **后续流转**：抽取稿可以继续进入 `output/summary/...`、`output/book-mirror/...` 或 wiki 编译；不要把抽取稿当作最终 wiki 结论。

### 编译输出

在 `output/wiki-compile/...` 下编写编译报告，总结：

- 导入的源文件
- 受影响的wiki页面
- 创建的页面
- 更新的页面
- **新建页命名对照（强制，当有映射时）**：凡本次**新建**的 `知识点-<主题>.md`，若主题名由源标题/小节标题**压缩或改写**而来，须逐条列出「**原标题（或源小节标题） → 采用页名/文件名**」。无新建页、或新建页主题与源标题字面一致且未压缩，可写「无命名压缩」或省略该小节。
- 索引/日志更新
- 未解决的后续事项

### 健康输出

在 `output/wiki-health/...` 下编写健康检查报告，总结：

- 发现的问题
- 受影响的页面
- 推荐的修复
- 来源空白

### 源材料总结与查重输出

- **总结稿**：无同质命中、或用户明确要求留档时，写入 `output/summary/<YYYY-MM-DD>/<slug>.md`（字段与模板见 `references/reference.md`）。
- **查重记录**：当判定为「已存在相同/等价总结」时，建议写入 `output/wiki-dedupe/<YYYY-MM-DD>-<slug>.md`，并在对话中复述其中列出的 wiki 路径链接。

### 书本镜像输出

- **镜像报告**：写入 `output/book-mirror/<YYYY-MM-DD>/<slug>.md`，先保留书本方法论与用户经验的对应关系，再决定是否编译进 wiki。
- **wiki 编译**：若镜像报告产生稳定方法论或对象页更新，继续写入/更新 `wiki/...`，并同步 `output/wiki-compile/...`、索引和维护日志。

## 查询与Wiki决策规则

使用此规则：

- 如果结果是短暂的、分析性的或问题特定的，仅保存在 `output/qa/...` 中。
- 如果结果是稳定的、可重用的，并作为概念或知识点具有广泛意义，推荐或执行归档到 `wiki/`。
- 当用户对输出反馈“不像我”“判断不对”“表达不对”“太官方”“太空”“AI味太重”“观点过时”“方向不对”等，判断是否属于稳定偏好或判断变化；若是稳定反馈，回写到 `wiki/自我模型.md`、`wiki/我的表达风格.md`、相关知识点页的 `摘要`/`概念`/`对比`/`概述与综合`，或人物/项目页的 `我的判断`/`当前结论`。若只是一次性改稿，只修改当前输出，不自动入库。

wiki值得输出的示例：

- 新的持久概念解释
- 跨来源合成，改进了现有知识页面
- 值得保存在 `对比` 下的澄清区别
- 纠正摘要，替换过时的wiki内容

## 必需行为

- 在读取大量源材料之前先读取索引。
- 优先更新现有wiki结构而不是创建重复页面。
- 除非模式明确要求，否则永远不要逐字镜像源文件到wiki中。
- 将源材料视为只读。
- 当wiki内容发生变化时，始终更新索引和日志。
- 始终将知识库Q&A结果保存到 `output/qa/...`。
- **多模态入库**：语音必须先转成文字摘要；图片/截图必须有说明、时间、场景和关联项目；视频必须抽取关键片段和结论；外部资料必须写「为什么收藏」和「对我有什么用」。缺少这些信息时先列入待补，不直接入 wiki。
- **普通知识点五段结构**：`知识点-*.md` 默认使用 `摘要`、`实体`、`概念`、`对比`、`概述与综合`；不要为了凑结构硬加当前结论、观点演化、已废弃观点或可复用规则。
- **原始资料抽取**：遇到会议、会谈、语音、图片、截图、视频、聊天或混乱材料时，先抽取时间、地点、人物、项目、事件、结果、用户判断和待确认问题，写入 `output/extract/...`，再决定是否编译进 wiki。
- **人物页事实/判断分离**：人物页必须使用「基本信息、互动时间线、当前状态、我的判断、关系状态、注意事项、相关项目、相关原始资料」结构；「基本信息」只写事实，「我的判断」只写用户判断并标注更新时间。
- **项目页当前结论**：项目页顶部必须有「当前结论」，包括是否值得继续、当前阶段、最大问题、下一步、我现在的态度；输出和决策时优先读当前结论，再读时间线。
- **已废弃观点**：当新判断取代旧判断时，追加 `已废弃观点` 表（时间 / 旧观点 / 为什么废弃 / 替代观点），不要让过时观点与当前观点平级。
- **书本镜像**：用户要求书与自己的经历/做法对应时，必须由用户指定书籍/方法论；先写 `output/book-mirror/...`，再经用户确认或依据明确后将稳定方法论或对象页更新编译进 wiki；不得把书本全文镜像进 wiki，也不得强行制造不存在的对应关系。
- **输出优先读取**：用户要求输出文章、PPT、项目规划、汇报或方案时，优先读取 `wiki/自我模型.md`、`wiki/我的表达风格.md`，再读相关知识点、人物/项目/方法论页，用已沉淀的判断和表达偏好组织答案。
- **对象页命名**：人物/项目页不得命名为 `知识点-<对象名称>.md`；人物用 `人物-<人物名称>.md`，项目页放入对应项目文件夹并命名为 `项目-<项目名称>.md`，该文件夹内其它专题仍用 `知识点-<主题>.md`。
- **源材料总结**：未经查重不得写入 `output/summary/...` 或等价路径；查重命中同质结论时，**必须先提示用户已有 wiki 路径**再等待明确指令（覆盖/合并/放弃）。
- **用户定向归集**：严格遵循用户给出的源路径与目标 wiki 页；优先更新已有页而非重复创建。  
- **知识点文件命名**：遵循上文 **「Wiki 知识点文件命名（主题优先）」** 与 **「简洁与可识别」**（中文主题默认 **4～12 字**）；新建页前自问「该主题是否已有 `知识点-….md`」以免同质分叉；新建页若压缩原标题，**必须**在 `output/wiki-compile/...` 中写清「原标题 → 采用页名」。
